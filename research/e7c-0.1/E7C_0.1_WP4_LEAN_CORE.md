# E7C/0.1 WP4 Lean core extension — review specification

Status: `draft; exact_head_review_required`

## 1. Scope

This separately reviewed WP4 package extends the accepted bounded Lean spike
with four connected obligations over the smallest useful multi-constructor
fragment:

1. deterministic evaluation;
2. successful preservation for variables, strict maps, source-preserving views
   and restrictions;
3. static-effect containment and ordered-ledger preservation; and
4. explicit correspondence between the Lean rules and the external WP2/WP3-S
   specification.

The package changes no canonical kernel text, release profile, schema, runtime
API, identifier or migration state.

## 2. Formal boundary

The Lean carrier collapses external indexed types into five fragment types:
`Config`, `Family Config`, source-preserving `View Config`, `Outcome Config` and
`Outcome (Family Config)`. Finite natural-number codes stand for admitted
configuration and declaration identities. This is a proof model, not a wire
representation.

`EnvironmentWellFormed` requires unique context/environment names, a typed
runtime binding for every admitted context entry, and no runtime binding
without a matching typed context entry. `InterpretationWellFormed` requires
unique declaration and interpretation names, a unique finite input row for
every strict-map or view table, a duplicate-free restriction carrier, a
complete interpretation for every admitted declaration, and no interpreted
declaration outside the admitted declarations.

These hypotheses are premises of successful preservation. They are not hidden
inside evaluation and are not inferred from a successful result.

WP2 effect rows use extensional finite-support predicates with idempotent union. The
separate `staticTrace` preserves order and repeated WP3 events. Typing relates
to the set; ledger order relates to the trace; emitted atoms map into the set.

## 3. External-rule correspondence

| Lean declaration | External source | Represented content | Deliberate abstraction or gap |
| --- | --- | --- | --- |
| `HasType.var` | WP2 §7 Variable | context lookup, empty effect | external indices and declaration environment are collapsed |
| `HasType.strictApp` | WP2 §7 Map application, `strict` policy | typed operand; finite extensional `evidence` and `partiality` set bound | rich atom payload is abstracted to declaration-keyed atoms |
| `HasType.sourceView` | WP2 §7 View, `source_preserving` | typed operand; `inquiry` and exact-return `alternatives` effects | view/index/policy parameters are collapsed |
| `HasType.restrict` | WP2 §7 Restriction | family operand; `alternatives` effect; outcome family | input/output indices and outcome extension are collapsed |
| `SpecEval.wp3Variable` | WP3-S §7 Variable | plain binding success and direct terminal-outcome propagation | resource step charge is omitted |
| `SpecEval.wp3Strict` | WP3-S §7 Map application, `strict` | argument-first propagation; ordered `evidence`, then `partiality`; domain failure; missing capability as `unsupported` | resource charges, unresolved obligations and structured detail are omitted |
| `SpecEval.wp3SourceView` | WP3-S §7 View, `source_preserving` | argument-first propagation; ordered `inquiry`, then `alternatives`; source-return value | resource charges and rich policy metadata are omitted |
| `SpecEval.wp3Restriction` | WP3-S §7 Restriction | deterministic finite filtering; argument-first propagation; `alternatives` event | candidate/resource charges and retained/excluded detail are omitted |

`spec_eval_matches_function` and `evaluate_has_spec_derivation` prove equality
between the two Lean encodings. They do **not** prove that either encoding is
adequate to the external WP3-S judgement. The table above is a reviewable
correspondence claim; an adequacy theorem needs a separately formalized
external syntax, indices, resources and translation relation.

## 4. Theorem inventory

| Lean theorem | Bounded claim |
| --- | --- |
| `spec_evaluation_deterministic` | any two Lean rule derivations for one term/environment/interpretation have identical outcome and ledger |
| `successful_type_preservation` | successful evaluation of a well-typed term under well-formed runtime inputs produces a value in the fragment carrier corresponding to the result type |
| `typing_effects_are_static` | the effect row in every fragment typing derivation equals the syntax-directed extensional set |
| `successful_ledger_exact` | a successful fragment evaluation emits exactly the syntax-directed ordered trace |
| `ordered_ledger_preservation` | every terminal result retains a ledger whose atoms are an initial segment of the syntax-directed trace |
| `ledger_effect_soundness` | every emitted atom belongs to the syntax-derived trace |
| `trace_member_is_static` | trace membership implies membership of the extensional static set |
| `typed_ordered_ledger_preservation` | typed terms preserve trace order independently of the WP2 set row |
| `typed_ledger_effect_soundness` | emitted atom containment transports from trace to the typed WP2 set |

The raw evaluator failing-child regression uses an ill-typed nested term; it is
an internal invariant, not admitted WP3-S coverage. An admitted strict-map case
checks domain failure and incurred ledger. The ledger theorems cover success
and propagated non-success in the raw evaluator. In this
unbounded projection, mandatory entries cannot themselves exhaust a bound;
therefore the general external resource-precedence theorem remains outside the
package.

## 5. Required regressions

The Lean source and repository controls must retain checks for:

- direct propagation of an outcome-typed variable;
- missing strict interpretation returning `unsupported`, not `domainError`;
- exact source-view ledger order;
- exact restriction result and ledger;
- typed strict-map domain failure with incurred ledger, and an explicitly raw
  evaluator failing-child prefix invariant outside the admitted fragment; and
- presence of explicit environment/interpretation well-formedness premises in
  successful preservation.

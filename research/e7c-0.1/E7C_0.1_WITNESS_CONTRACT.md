# E7C/0.1 B1 witness and independent replay contract — review candidate

Status: `witness_contract_drafted_unimplemented`

Authority: WP3-S accepted at PR #37 head `bae84fb73e…`, merged as
`c13d77dc5b…`

Canonical baseline: E7G-T v0.12.1-experimental, `RGP/0.1`, revision RGP2

This package defines the slice-specific witness boundary required before WP3-I.
It is a specification only. It contains no evaluator, witness emitter, replay
checker, stable serialization, public API, proof, profile adapter or kernel
change. Acceptance of this contract may authorize a disposable WP3-I branch;
it does not complete the later WP7 witness work package.

## 1. Purpose and claim boundary

A B1 witness is replay material for one admitted, resource-indexed evaluation
under pinned rules and inputs. It records enough canonical data for a separately
implemented checker to reconstruct the static judgement and repeat the dynamic
checks without trusting evaluator-internal state.

Checker acceptance may establish only this bounded claim:

> Under the pinned B1 syntax, rule, declaration, interpretation and resource
> editions, the supplied admitted term and runtime inputs replay to the recorded
> terminal outcome, ordered ledger and resource progress.

It does **not** establish that source material is true, complete, authentic or
current; that a source or operator has legitimate domain authority; that an
interpretation is scientifically or externally correct; or that a result is
valid outside the recorded scope, time, model and policy editions.

## 2. Witness envelope

`Witness[j,omega]` is a canonical finite record with these mandatory groups:

| Group | Required contents | Replay use |
|---|---|---|
| identity | witness edition `omega`, judgement class `j`, fixed claim class `bounded_derivation_replay`, witness identifier | select schema and prevent cross-class reuse or claim escalation |
| rule pins | calculus/B1 edition, WP2 static-rules identity, WP3-S semantics identity, outcome-extension edition | select the exact admitted rules |
| evaluation claim | canonical term, claimed static type/effect row, terminal outcome, ordered ledger, resource-progress snapshot | state the derivation to reproduce |
| static inputs | canonical declaration environment and all nominal identities/editions referenced by the term | repeat admission and typing |
| runtime inputs | canonical value environment, interpretation package, capability facts, obligation resolutions, finite carriers and equality/order tables | repeat evaluation without evaluator memory |
| resource input | complete `beta` record and policy edition | reproduce charge points and exhaustion |
| derivation record | canonical rule tree, child order, charge events, ledger appends, candidate keys and terminal rule | locate and audit every claimed transition |
| external assumptions | source references, provenance statements, access/authority assertions, scope, time, modality and model/policy labels | bind opaque assumptions without upgrading them |
| integrity | canonical encoding/digest editions, ordered non-integrity group digests and root digest | detect mutation and substitution without a self-referential hash |

The canonical term, declarations, values and interpretation inputs must be
present as replayable data, or be resolved by digest to immutable bytes supplied
to the checker. A digest alone proves neither availability nor meaning. If any
required bytes are absent or redacted, the object is an audit commitment, not a
replayable B1 witness, and the checker returns `missing_replay_material`.

External source content may be included or referenced for provenance, but the
checker treats it as opaque input. Its digest binds bytes; it does not certify
their truth, authorship, authority or correspondence to the world.

Identity construction has two phases. First construct canonical **digest
payloads** with every self-reference omitted:

- the identity-group digest payload omits `witness_identifier`;
- the evaluation-claim digest payload omits
  `terminal_outcome.success.optional_witness` when the terminal outcome is
  successful;
- derivation-node outcomes never contain the envelope witness identifier; and
- every derivation-node digest payload omits its own `node_id`.

Derive node identifiers bottom-up. A node identifier is the digest of its
canonical node digest payload, which may contain already-derived ordered child
identifiers but never its own identifier. Bind each resulting `node_id` to its
node only after that node digest has been computed.

Next compute each non-integrity group digest over its canonical digest payload.
The root digest covers the encoding edition, digest edition and ordered
`(group_name, group_digest)` sequence. Derive the witness identifier as
`omega:root_digest`. Only after the root digest is fixed, bind that identifier
to both the top-level `witness_identifier` and, for a successful claimed result,
`terminal_outcome.success.optional_witness`.

The integrity group, node identifiers and both witness-identifier occurrences
are therefore final bindings, not inputs to the hashes that derive them. During
replay the checker omits those exact fields, recomputes every node and envelope
digest, then verifies that every final binding equals its derived identifier.

## 3. Canonical derivation record

Each derivation node contains:

```text
node_id
rule_id and rule_edition
canonical input term identity
child_node_ids in evaluation order
pre-state counters
completed step/candidate/ledger charges
ledger entries appended at this node
candidate keys examined in canonical order
terminal outcome and post-state counters
```

Node identifiers are derived bottom-up using the digest-payload rule above. A
node's canonical hash input explicitly excludes its own `node_id`, while its
ordered child identifiers remain included. The derived root-node identifier is
then covered by the derivation-record group and envelope integrity construction.
Unknown mandatory fields, rule editions or outcome extensions are rejected;
they are never ignored as forward-compatible decoration.

The derivation record is an audit index, not trusted evidence. The checker
recomputes charges, candidate order, ledger entries and outcomes from the pinned
inputs. A self-consistent fabricated tree fails if recomputation disagrees.

The only admitted claim class is `bounded_derivation_replay`. A witness that
declares or implies `source_truth`, `authority_verified`, `external_validity` or
another stronger class is rejected with `authority_claim_escalation` before its
derivation is considered.

## 4. Independent replay relation

The separately implemented checker defines:

```math
Check_{omega}(w, R) = accepted(replayed\_claim)
                    \mid rejected(diagnostic),
```

where `R` is the finite resolver containing immutable artifacts named by digest.
The checker must not import evaluator code, deserialize evaluator-private
objects, call evaluator callbacks, trust cached evaluator decisions or require a
network service.

The replay trusted base is limited to the checker implementation, its pinned
canonical decoder, digest algorithms, exact WP2/WP3 rule editions and explicitly
named primitive equality/order decoders. Shared canonical data structures are
permitted; shared evaluator control flow, cached outcomes and trace-generation
code are not. Any implementation claim must identify versions and dependencies
of this trusted base.

Replay proceeds in this fixed order:

1. validate envelope shape, canonical encoding, digests and witness edition;
2. resolve every mandatory artifact by digest and verify its bytes;
3. reject edition, identity, scope or policy mismatches;
4. rerun WP2 admission, typing and static effect inference independently;
5. validate the value environment and interpretation package against the pinned
   declarations and capabilities;
6. reevaluate the term using an independently implemented WP3-S rule engine and
   the recorded `beta` policy;
7. recompute canonical candidate order, every resource charge and every ordered
   ledger entry;
8. compare the recomputed static judgement, outcome, ledger, progress and root
   derivation identity with the witness claim;
9. return `accepted` only on exact equality of every observable component.

Replay never substitutes the current repository head, a newer edition or a
host default for a missing pin. Replaying under a different edition is a new
claim, not validation of the original witness.

## 5. Interpretation and authority boundary

The interpretation package is replay data, not evaluator authority. For B1 it
must expose finite, deterministic material sufficient for the referenced term:

- finite canonical map and domain tables;
- view/projection records and their preservation/loss declarations;
- restriction membership tables and canonical family order;
- reconstruction carriers plus equality and ordering tables;
- classification result tables;
- capability facts and explicit obligation resolutions.

No interpretation field contains executable host-language code. A later
canonical procedure language would require its own syntax, semantics, admission
and witness-contract review before use here.

The checker confirms that this material was used consistently with the pinned
rules. It does not confirm that the material correctly describes an external
system or domain. `authority_asserted`, `authority_source` and temporal/scope
fields are recorded assumptions. They are never converted into
`authority_verified` by replay.

## 6. What acceptance can and cannot establish

| Claim | After checker acceptance |
|---|---|
| witness bytes and referenced artifacts match their digests | established relative to the named digest and encoding algorithms |
| term is admitted and typed under pinned WP2 rules | established for the supplied canonical inputs |
| recorded outcome, ledger and progress follow pinned WP3-S rules | established by independent bounded replay |
| candidate enumeration is complete | established only for the pinned finite carrier and completed resource-bounded run |
| source bytes are authentic, complete, current or true | not established |
| source/provider has legitimate domain authority | not established |
| interpretation tables model the external domain correctly | not established |
| mathematical laws hold for all terms or models | not established |
| evaluator implementation is correct in general | not established |
| security, empirical effectiveness or product fitness | not established |

An accepted witness is evidence for one replayed derivation, not a proof by
checksum and not a transfer of authority from the checker to the source.

## 7. Terminal outcomes and ledger preservation

The sidecar witness may describe every terminal outcome. For `success`, its
identifier occupies the reviewed `optional_witness` slot only in the final
binding step; that nested field is omitted from the evaluation-claim digest
payload. Derivation-node outcomes carry no envelope witness reference.
Non-success tags remain exactly the WP3-S tags and are accompanied by the
sidecar without being wrapped or replaced.

Replay must reproduce:

- direct propagation of an outcome-typed variable;
- short-circuit propagation of every non-success argument;
- step, ledger-entry and candidate charge precedence;
- the complete ordered ledger prefix for success and non-success;
- canonical retained/excluded alternatives;
- complete reconstruction fibres, never successful partial prefixes.

## 8. Rejection diagnostics and adversarial cases

The checker uses structured rejection diagnostics at least for:

```text
malformed_witness
unknown_witness_edition
unknown_mandatory_capability
missing_replay_material
digest_mismatch
edition_mismatch
identity_mismatch
static_judgement_mismatch
derivation_order_mismatch
resource_accounting_mismatch
ledger_mismatch
outcome_mismatch
authority_claim_escalation
```

Required adversarial fixtures alter one item at a time: term, declaration
edition, runtime value, resource bound, candidate order, ledger order/detail,
terminal tag, derivation child order, source digest, authority assertion and an
unknown mandatory field. None may be accepted through fallback or normalization.

## 9. WP3-I entry gate and first evaluator tests

WP3-I remains blocked until review accepts this contract's replay inputs, claim
boundary, independent-checker separation, canonicalization requirements and
adversarial cases. Contract acceptance authorizes only a disposable evaluator
and checker branch; it does not stabilize a schema or API.

The first WP3-I tests must cover:

1. direct and nested non-success outcome propagation without double wrapping;
2. zero-step lookup and coincident resource/failure precedence;
3. exact ordered ledgers, including retained prefixes on failure;
4. exhaustive canonical fibre reconstruction and rejection of partial success;
5. witness replay by a separately implemented checker;
6. tamper, missing-material, edition-mismatch and authority-escalation rejection.

No evaluator-produced witness may be treated as conformant until the independent
checker reproduces its claim from canonical inputs.

## 10. Review gate and non-claims

The witness contract may pass only if review confirms:

- all replay-relevant syntax, rule, declaration, interpretation and resource
  inputs are pinned and available as canonical data;
- hashes bind bytes but are never treated as proofs of truth or authority;
- the checker recomputes rather than trusts evaluator decisions or traces;
- accepted claims are limited to one bounded derivation under recorded inputs;
- source truth, domain authority and external-model correctness remain outside
  the claim;
- redaction or missing bytes cannot silently degrade replay;
- every terminal outcome preserves its ordered ledger and resource behavior;
- WP3-I and any stable witness schema/API remain blocked until review.

This contract makes no theorem, implementation, performance, security,
canonical-kernel, adapter or product-readiness claim.

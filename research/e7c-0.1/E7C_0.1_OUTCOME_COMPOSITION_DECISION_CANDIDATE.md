# Decision candidate — explicit composition after an `Outcome`

Status: `owner_authorized_for_research_implementation; no_semantic_change_in_this_record`.
Base: PR #89 merge `d6cd9dd121e705ded6f560e74a088d480c663fed`.
Affected decision surfaces: ADR-001 (binder/context), ADR-004 (sequential
effects), ADR-005 (partiality), ADR-007 (witness), ADR-011 (outcome boundary).

## The concrete failure

The accepted B1 checker rejects this term before evaluation:

```text
apply(strict_normalise,
      apply(total_identity, var source_config))
```

The inner application has type `Outcome[Config["Sigma-A"],"core-1"]`;
`strict_normalise` requires `Config["Sigma-A"]`. The checker reports
`E7C-T002`. This is asserted as a negative regression in
`test_e7_ir_views_b1.py`. WP2 and WP3-S explicitly make `Outcome` terminal:
they forbid implicit flattening, values beneath `Outcome`, declarations
consuming it and an outcome eliminator. PRs #85–#89 therefore lower only
direct-variable operations. Their successful finite differentials do not
establish composition or complete WP6.

## Decisions available

| Candidate | What changes in a separately versioned successor | Benefit | Proof/review cost |
|---|---|---|---|
| A. Keep terminal-only | No language change. Compile independent operations whose operands are already bound values. | B1 stays closed and accepted rules stay intact. | General sequential programs stay unavailable; WP6 completeness must be scoped accordingly. |
| B. Add an explicit success binder | A new typed constructor consumes the success value of `Outcome[A,xi]` and runs a continuation; non-success propagates with its exact tag and already incurred ledger. | Allows selected sequential maps without implicit coercion. | Must define fresh variable scope, edition rules, outcome-extension compatibility, ordered charges, effect composition, substitution/preservation and checker replay. |
| C. Add explicit exhaustive outcome cases | A typed case term handles success and each failure/unknown tag separately; resource exhaustion treatment must be specified. | Lets a program intentionally respond to non-success. | More rules, potential masking of failure or authority boundaries, stronger progress and witness obligations. |

**Recommended next research candidate: B, limited to a new, opt-in edition.**
Keep existing B1 closed and allow only an explicit constructor such as
`bind_success(t, x. u)`; no implicit `apply` over an outcome. The success
branch admits `x:A` and requires the continuation to be well-typed under a
scoped context. On non-success, preserve the precise terminal tag and
diagnostic/obligation/bound, append no continuation ledger, and record the
outer constructor's declared charge. This is a design direction for review,
not an accepted rule. Do not allow a `resource_limit` to be swallowed by a
success continuation. An exhaustive case constructor, if needed, should be
a separate later decision.

## Required before implementing B

1. Specify binder syntax, capture-avoiding substitution and admissible value
   type, with no `Outcome` in the success payload unless separately approved.
2. Pin compatibility of `xi` editions and explicit result type; distinguish
   terminal computation from stored outcome values and avoid double wrapping.
3. Define static sequential effect composition and exact incurred ledger
   ordering for success, `domain_error`, `unsupported`, `undetermined` and
   `resource_limit`, including coincident budget exhaustion.
4. State denotational bind and prove or bound progress, successful type
   preservation, effect/ledger bound, determinism and source/IR correspondence.
5. Implement source evaluator and independently coded checker rules with
   positive and adversarial fixtures; only then add a new versioned IR
   lowering. Keep the v0.12.1/RGP2 canonical source and old B1/IR editions
   unchanged. No consumer, data or API migration follows automatically.

The owner approved research and implementation of an explicit success-only
sequencing rule in a new provisional edition on 2026-09-24. The mandate's
§14.5 decision prerequisite is therefore met for that bounded work. The
implementation must retain the non-success distinctions and remain separately
reviewable before acceptance. This record does not itself close ADR-001,
ADR-004, ADR-005, ADR-007 or ADR-011 or make a profile/product readiness claim.

# EEC-Q two-stage all-input relation (provisional proof package)

Base: main `7cc35af720ca0897e4d9c303a31e6840bb48d9bc` (PR #101 merge).
Source: published experimental v0.12.1/RGP2 §§X.5–X.6; selected predicate
editions `FG3-JOINT-COORD0-ABSENT-AB/0.1-provisional` and
`FG3-JOINT-COORD1-ABSENT-BC/0.1-provisional`. No source/profile migration.

## Relation and premises

For an admitted, canonically ordered binary FG3 Joint, each row is
`(left graph, right graph, exact rational coefficient)` with a unique pair,
nonzero reduced rational and fixed predicate editions. The first predicate
tests `left.ab`; only rows without it reach the second, which tests
`right.bc`. Both the graph pair (including tags) and rational value are
unchanged in their destination. An empty Joint is admitted. Duplicates,
zero or unreduced coefficients, malformed graph labels, edition changes and
oversize inputs are outside source admission.

In Lean, `source` uses three disjoint filters and `ir` uses a separate
recursive case split. For **every** `List Row`, without a cardinality bound:

- `all_rows_partition_agreement` proves the two partitions equal, including
  order, complete graph pairs and rational coefficients.
- `exact_rational_row_route` proves each input row reaches the declared
  destination **as the identical `Row` term**, so its correlated graph pair,
  tag and exact `Rat` value are preserved without a value erasure.
  `all_key_occurrences_conserved` checks the count for each graph pair.
  Together with source admission's unique pairs, this gives exactly one
  unchanged destination per admitted row, including negative coefficients.
- `sufficient_resource_observation_agreement` compares the two Lean
  successful observations, including row order, full partition, checked-row
  ledger and second-stage resource counts. Its premises require the second
  stage's remaining step and ledger budgets each to be at least `1 + n`,
  where `n` is the length of the first stage's retained list.

The **external relation** additionally requires: Python source admission
agrees with Lean graph/row decoding and canonical ordering; the first-stage
source and IR terminal, retained Joint, excluded Joint, ledger and progress
agree; both first-stage capability and obligation are resolved; the second
stage is available and resolved; and after the first stage each resource
budget has at least `1 + n` left. For a successful original Joint of `m`
rows, the total requirement is `step_bound, ledger_bound ≥ 2 + m + n`.
The Python runner and independent IR executor must then yield the same full
success observation: terminal and three complete portions, ledger, completed
steps and progress. The Lean theorem covers the **mathematical stage-two
model** under these premises; executable source/IR checks cover concrete
admitted documents. It is **not** a proved general Python-to-Lean refinement.

## Premise attacks and boundary

`test_e7c_eecq_two_stage_all_input.py` enumerates all support subsets up to
two rows over nine correlated graph pairs with both rational signs. Each
successful source and independently executed IR observation is compared to a
third plain row enumerator. It also tests the exact one-unit-short resource
boundary for each case; identical marginals with different Joint tables;
duplicate, zero and unreduced rows rejected at admission; first unsupported,
second undetermined, zero-budget exhaustion; and a re-digested forged
first-stage ledger rejected by IR replay. These finite checks are evidence
about implementations and are separate from the all-list Lean proof.

Resource exhaustion, unsupported and undetermined observations do **not**
have the Lean success relation: a zero-step budget cannot produce a
partition; unavailable interpretation does not perform a successful second
restriction. Their typed, disjoint terminals and progress remain covered by
the prior finite #101 gate and these counterexamples, without claiming an
all-input theorem for those branches.

**Unproved links:** source JSON admission to Lean `Row` (including
canonicalization and ordering); all-input Python first-stage source/IR
agreement; Python/IR step-by-step relation to the Lean functions and ledger
representation; all-input resource/failure trace relation; general EEC-Q
semantic adequacy; external reproduction. The Lean result does not certify
profile conformance or product performance.

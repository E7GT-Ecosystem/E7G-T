# E7C/0.1 proof-assistant spike and selection record

Status: `selection_deferred; lean_bounded_spike_accepted; lean_core_extension_draft`

Baseline: `2dcd06c6fda9c13b9ce40500bc835912e06cd245`

WP4 requires a representative spike covering substitution, preservation and
one strict-partial-map property before selecting a proof assistant. No Lean 4,
Rocq/Coq or Isabelle executable is available in the local builder environment.
A path-scoped repository workflow can now execute the Lean candidate. This
record compares the candidates and fixes the spike acceptance test; it does not
select a winner.

## 1. Required common spike

Each candidate must formalize the same nucleus:

- B1 types sufficient for `Config`, `Outcome` and strict `Map`;
- binder-free variables and unary map application;
- finite reusable contexts;
- explicit `success` and `domain_error` outcomes;
- one finite interpretation table with no host callbacks;
- typing substitution;
- successful type preservation;
- strict-map failure is not success with an empty value.

The submission must name tool version, standard-library version, axioms,
admitted lemmas, generated code if any, build command and trusted base. No
`sorry`, `admit`, opaque external oracle or unreviewed classical axiom may occur
in the accepted comparison artifact.

## 2. Candidate comparison

| Criterion | Lean 4 | Rocq/Coq | Isabelle/HOL |
| --- | --- | --- | --- |
| Inductive syntax and relations | strong native support | mature native support | strong datatypes/inductives |
| Executable finite functions | strong; convenient extraction/runtime path | strong; mature extraction | strong code generation |
| Dependent typing ergonomics | strong but elaboration-sensitive | strongest established dependent core | HOL encoding requires different style |
| Proof automation | simp, aesop and ecosystem tactics | mature tactics and libraries | strong simplifier and automation |
| Small trusted kernel | yes | yes | LCF-style trusted inference kernel |
| Fit with later algebra/category work | mathlib is attractive | Mathematical Components/UniMath options | AFP and locale machinery are attractive |
| Integration burden for this Python research package | likely low-to-medium | medium | medium-to-high |
| Current environment evidence | bounded feasibility spike accepted and merged after CI build and axiom audit; separately scoped core extension is draft | unavailable | unavailable |

These are planning observations, not benchmark results.

## 3. Decision rule

Run all three spikes where practical. Select only after comparing:

1. zero unproved admissions;
2. clarity of theorem statements against the WP2/WP3-S notation;
3. proof size and robustness under one added constructor;
4. reproducible non-interactive build;
5. ability to export/check finite fixtures without making extraction the
   semantics;
6. maintainability by an independent reviewer.

If only one tool can be executed, record that as an environment limitation and
make a provisional tool choice, not a comparative conclusion. The selected
assistant will mechanize only the formal nucleus and selected adapter laws, not
the inherited kernel prose.

## 4. Current decision

`selection_deferred; lean_bounded_spike_accepted; lean_core_extension_draft`.

The bounded Lean 4.34.0 feasibility spike was accepted at exact head
`028922f98f3e31f0c9f97ddb0171c3bd83c2f526` and merged as
`2dcd06c6fda9c13b9ce40500bc835912e06cd245`. Its build and axiom audit passed
with only Lean's standard `propext` allowlisted. That acceptance closes the
bounded feasibility gate only; it does not prove that the model adequately
represents E7C or select Lean permanently.

The separately scoped package in `proof-packages/lean-core` now attempts the
next nucleus: determinism, successful preservation across variables, strict
maps, source-preserving views and restrictions, effect/ordered-ledger
preservation, and an explicit external-rule correspondence record. It remains
draft and requires exact-head review. Its equality theorem between the Lean
functional and inductive evaluators is not an adequacy theorem for WP3-S.

Lean remains the provisional first candidate because its inductive definitions,
dependent types, simplifier and ecosystem fit the expected work and repository
CI can execute it. Rocq and Isabelle have not been run. Tool selection remains
deferred pending the comparison work described above.

## Sort execution model

`E7CJointSortConstructorSemantics.lean` defines an abstract comparison-and-
insertion operational semantics. Every insertion trace records comparator
outcomes and a list write; ties leave the earlier item first. A recursive sort
trace composes those events. Lean proves by induction that its resulting key
sequence equals #144's `sortJointKeys` model. It does not take a completed
sorted list as a premise.

The bridge to the host requires explicit operation observations: identity-key
extraction agrees with the pinned tagged tuple; tuple comparison agrees with
`compareJointIdentity`; and the runtime comparison and list-write events form
the recorded trace. This is an abstract sorting semantics, not a model of
CPython's Timsort internals. Runtime adequacy of `list.sort`/`sorted` to the
trace remains assumed and open. In particular, this proves no claim about
CPython's C implementation.

The Lean comparator cases establish AB before AC and a null tag before an
empty-string tag. The test suite checks the full three-edge order, the same
tag distinction, duplicate aggregation, exact rational coefficients,
cancellation, and constructor rejection.

## Constructor execution model

`runConstructorRows` checks a positive arity, the outer tuple, each row's
atom-tuple/exact-Fraction/nonzero conditions, and the constructor's canonical
order check. Accepted rows are returned by an explicit recursive run, and Lean
derives that the returned list is exactly the visited input sequence. A
row-level failed check derives rejection. The host premises are the individual
exact-type/Fraction/check outcomes and the result of the adapter's
`keys == sorted(set(keys))` validation; this increment does not assume a
constructed result. Exact Python type behavior (including bool-versus-int),
the concrete Config type check, and the runtime validation branch are tested
against the adapter. Their CPython adequacy remains open.

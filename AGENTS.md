## Start and checkpoint protocol

1. Inspect current code, default-branch head, worktree, open PRs and the product build plan. Reconcile the assignment with actual implementation; do not restart completed milestones from stale guidance.
2. State the builder/thread label, exact baseline, branch, bounded work package, files/interfaces and next acceptance gate. Record a short check-in in the development PR or coordination board. Do not claim another agent has acknowledged.
3. Preserve work in progress. Use an isolated branch and respect its declared writer. Recheck main before publishing; never force-update another contributor's branch or reset a shared worktree.
4. Before changing shared formats, semantics or source pins, name affected consumers, preservation/loss, migration impact and compatibility check. Retain native product identities unless an explicit migration is intended.
5. At a milestone, report the exact commit, meaningful commands/results, skipped checks, unsupported capabilities and next step. Distinguish published guidance, builder acknowledgement and verified compliance.
6. Read relevant coordination notes at the next checkpoint. Repository activity cannot reveal all unpublished work in other chats.

Follow the user's current task and standing authorisations. Do not repeat permission requests for already-authorised work. Finish reversible work within scope. This file does not authorise external messages, provider expenditure, private-code publication or bypassing repository checks. Keep public guidance free of private implementation or collaborator material.
